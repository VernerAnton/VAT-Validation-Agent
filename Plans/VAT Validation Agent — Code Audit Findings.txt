## 🔴 Critical Issues (Will Cause Runtime Failures)

### 1. Missing `zod` dependency in `websearch-server`

**File:** [`websearch-server/package.json`](websearch-server/package.json:11)

**Problem:** `websearch-server/src/index.ts` imports `zod` at line 5 (`import { z } from 'zod'`), but `zod` is **not listed** in `websearch-server/package.json` dependencies. It only exists as a devDependency transitively through `@modelcontextprotocol/sdk`.

**Impact:** When deployed to Railway (production `npm start`), the `node_modules` are built from `dependencies` only. If `zod` is not hoisted as a transitive dependency, the server will crash at startup with `Cannot find module 'zod'`.

**Fix:** Add `"zod": "^3.23.8"` to `websearch-server/package.json` dependencies (same as sandbox-server).

> **Review note — severity downgrade to 🟡 Moderate:** `zod` is a direct (non-dev) dependency of `@modelcontextprotocol/sdk`, so npm *will* hoist it into `node_modules` in production. This won't crash today. The real risk is future npm hoisting changes or SDK dependency changes. Still a legitimate fix for dependency hygiene, but "Will Cause Runtime Failures" is overstated.

### 2. MCP Client Sends 3 HTTP Requests Per Tool Call

**File:** [`streamlit-app/mcp_client.py`](streamlit-app/mcp_client.py:52)

**Problem:** The `_call()` method sends **three separate HTTP POST requests** for every single tool/resource call:
1. `initialize` (id=1)
2. `notifications/initialized` (no id, notification)
3. The actual method call (id=2)

For 185 countries × 3 search queries each = 555 search calls, this means **1,665 HTTP requests** just for initialization overhead, plus 555 actual tool calls. Each request also gets its own `httpx.Client` context.

**Impact:** 
- **3× more latency** than necessary (each country validation involves 3× the HTTP round trips)
- **3× more load** on Railway servers
- The `initialize` + `initialized` pattern is designed for stateful MCP sessions. In stateless mode (which these servers use), the server creates a fresh `McpServer` per POST request, so the initialize call has **no effect** on the subsequent actual call. It's wasted traffic.

**Fix:** Either:
- (a) Remove the initialize/initialized calls entirely for stateless servers, or
- (b) Batch initialize + actual call into a single request if the server supports it

> **Review note — confirmed ✅:** All three servers use `sessionIdGenerator: undefined` (stateless mode) and create a fresh `McpServer` per POST. The `initialize` and `initialized` calls go to server instances that are immediately discarded — they have zero effect on the third POST that carries the actual method call. The 3× multiplier math is accurate. While the MCP Streamable HTTP spec technically requires initialization, there's no session continuity between the three POSTs in stateless mode, making it pointless.

## 🟡 Moderate Issues (May Cause Problems)

### 4. `sandbox-server` Uses `zod/v3` Import Path

**File:** [`sandbox-server/src/index.ts`](sandbox-server/src/index.ts:8)

**Problem:** Line 8 imports from `zod/v3`:
```typescript
import { z } from 'zod/v3';
```

This is a compatibility import path that may not exist in all versions of zod. The comment says "Import from zod/v3 for compatibility with the MCP SDK's internal zod-compat layer", but this is fragile and version-dependent.

**Impact:** If `@modelcontextprotocol/sdk` updates its internal zod requirements, this import path could break.

**Fix:** Use standard `import { z } from 'zod'` and ensure the zod version in package.json is compatible with the MCP SDK.

> **Review note — severity upgrade to 🔴 Critical:** This is more dangerous than originally assessed. [`sandbox-server/package.json`](sandbox-server/package.json:15) pins `"zod": "^3.23.8"` — but `zod/v3` as a subpath export is a **zod v4+ feature** (it exists so zod v4 consumers can access the v3-compatible API). In zod 3.x, the `zod/v3` subpath does not exist. This import only works today because the MCP SDK internally bundles or re-exports it. If the SDK changes its internal bundling, this will break immediately. Should be changed to `import { z } from 'zod'` and the zod version should be verified for SDK compatibility.

### 5. No `requirements.txt` Pin for `streamlit-app` Python Version

**File:** [`streamlit-app/requirements.txt`](streamlit-app/requirements.txt:1)

**Problem:** The `requirements.txt` has no `python_version` constraint. Railway's nixpacks will pick whatever Python version is available, which could be incompatible with the pinned package versions.

**Impact:** Potential dependency resolution failures on Railway.

**Fix:** Add a `runtime.txt` or `nixpacks.toml` specifying Python 3.11+.

> **Review note — confirmed ✅**

### 8. `format_rate` Used on Float Values in Review UI

**File:** [`streamlit-app/app.py`](streamlit-app/app.py:715-717)

**Problem:** Lines 715-717 call `format_rate()` on `data['stored_rate']`, `data['found_rate']`, and `data['rate_diff']`. These values come from the `validation_results` dict where they are stored as Python `float`. The `format_rate()` function in [`vba_parser.py`](streamlit-app/vba_parser.py:69) is designed for VBA output formatting, not UI display.

**Impact:** Works correctly but is semantically misused. `format_rate(0.0)` returns `"0"` which is fine for display.

**Status:** NOT A BUG — works correctly, just a design concern.

> **Review note — confirmed ✅:** [`format_rate()`](streamlit-app/vba_parser.py:69) just strips `.0` from integers and uses `f"{rate:g}"` for floats. Perfectly fine for UI display.

### 9. `scan_log_buffer` Grows Unbounded During Scan

**File:** [`streamlit-app/app.py`](streamlit-app/app.py:228)

**Problem:** The `_sandbox_log()` function appends to `st.session_state.scan_log_buffer` which grows for the entire duration of the scan. For 185 countries with 3 queries each plus LLM calls, this could be 1000+ log entries. Each sync to sandbox rewrites the entire buffer.

**Impact:** 
- Increasingly slow sandbox writes as scan progresses
- Potential memory issues for very large scans

**Fix:** Consider appending-only writes or periodic flushes.

> **Review note — confirmed ✅, but impact is overstated:** For the actual data sizes (text log lines, ~925 entries for 185 countries), memory won't be an issue. The real concern is O(n²) I/O — each of the ~925 sandbox writes sends progressively more data. Still worth fixing but won't cause crashes.

### 10. `computeLCS` O(n×m) Memory Issue for Large Files

**File:** [`sandbox-server/src/index.ts`](sandbox-server/src/index.ts:191-228)

**Problem:** The `computeLCS` function creates a 2D array `dp[m+1][n+1]`. For files with many lines, this can consume significant memory. The fallback at line 196 checks `m * n > 1_000_000` but the VBA database file has ~185 lines, so `185 * 185 = 34,225` which is fine.

**Status:** NOT A BUG for current use case, but the `simpleLCS` fallback is too naive (it just checks if lines exist in both files, losing ordering information).

> **Review note — confirmed ✅:** [`simpleLCS`](sandbox-server/src/index.ts:234) uses `Set.has()` which loses ordering — it's a set intersection, not a subsequence. Correct assessment.

## 🔴 Issues Missed by Original Audit

### 17. `file-vault-server` Shares Single `McpServer` Instance Across Requests (Concurrency Bug)

**File:** [`file-vault-server/src/index.ts`](file-vault-server/src/index.ts:29)

**Problem:** The `McpServer` is created **once** at module level (line 29), but [`server.connect(transport)`](file-vault-server/src/index.ts:107) is called on every incoming POST request (line 107). This means the same server instance gets `connect()`ed to multiple transports over its lifetime.

Compare with [`websearch-server/src/index.ts:156`](websearch-server/src/index.ts:156) which correctly creates a **new** `McpServer` per request via `createMcpServer()`.

**Impact:** If two requests arrive concurrently, the shared `McpServer` instance may have its internal transport state corrupted. The SDK's `connect()` method may overwrite the previous transport reference, causing one request to fail or receive the other's response.

**Fix:** Follow the websearch-server pattern — create a new `McpServer` instance per POST request:
```typescript
app.post('/mcp', async (req, res) => {
  const server = createMcpServer(); // new instance per request
  const transport = new StreamableHTTPServerTransport({ sessionIdGenerator: undefined });
  // ...
});
```

**Severity:** 🔴 Critical — can cause silent data corruption under concurrent load.

---

### 18. Qwen Model `<think>` Tags Not Stripped from LLM Response

**File:** [`streamlit-app/app.py`](streamlit-app/app.py:323-328)

**Problem:** The model `qwen/qwen3.6-plus` on OpenRouter may return thinking tokens wrapped in `<think>...</think>` tags within the response content. The JSON parsing code at lines 323-328 strips markdown code fences (```` ``` ````) but does **not** strip `<think>` blocks.

If the model returns:
```
<think>Let me analyze the VAT rate for Germany...</think>
{"standard_rate": 19.0, ...}
```

The `json.loads()` call will fail with `JSONDecodeError` because the content starts with `<think>`.

**Impact:** Intermittent JSON parse failures depending on whether the model includes thinking tokens. Falls back to the error handler which sets `confidence_score: 0.0` and `needs_human_review: true` — not a crash, but degrades results.

**Fix:** Add `<think>` tag stripping before JSON parsing:
```python
# Strip <think>...</think> blocks if present
content = re.sub(r'<think>.*?</think>', '', content, flags=re.DOTALL).strip()
```

**Severity:** 🟡 Moderate — causes degraded results, not crashes.
